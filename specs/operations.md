# Operations
- Dev and production are real Azure Container Apps/Jobs deployments of a permanently paper-only POC. Dev uses monitored `shadow`; production releases land `disabled`/Manual before evidence-gated promotion to scheduled `paper`. Until that promotion path is implemented, reviewed, and commissioned, production remains disabled/Manual.
- Releases use OIDC/Entra, least privilege, private PostgreSQL, immutable image digests, distinct runtime/owner/operator identities, replay-safe migrations, exact-SHA evidence, and independent alerts.
- Development requires the exact current main/workflow source and successful push CI. Full runs publish an immutable attempt-bound shadow receipt containing image/target binding, manual shadow identity, observed execution timing, and immutable workflow/actor IDs. Receipt validation/publication failure participates in disabled/Manual recovery; a missing receipt cannot publish successful development status.
- Full production admission loads the latest development attempt for that exact SHA, verifies its actual required GitHub jobs and immutable receipt, and repeats main/run/attempt checks before Azure access. A newer pending/failed run, rerun, foundation, green wrapper, missing/ambiguous artifact, or superseded source cannot fall back to an older success. Fresh foundation commissioning remains separate and requires current-main CI, not a pre-existing workload deployment.
- Automatic production releases follow `Azure deploy dev` completion only while the factory is human-activated. The exact triggering development run and attempt must still be the latest verified evidence; automatic events always select `full`. Factory activation is rechecked immediately before Azure access. Manual foundation/full commissioning remains separate. Both paths still end disabled/Manual, without authorizing first paper activation or factory completion.
- Any failed identity, migration, smoke, reconciliation, backup/restore, evidence, schedule, or alert check stops the release; rollback first forces `Manual` plus `disabled`.
- Existing production releases require an ops-owned, signed-source-bound cutover fence before forced disable. A healthy open position or active lease defers the upgrade without changing mode, schedules, credentials, images, or balances; malformed, expired, stopped, or unreconciled state blocks it.
- Runtime admission and paper execution reject an unreleased fence; the runtime role has read-only fence access. Ownership and the six-hour deadline are revalidated at mutation boundaries, including forced disable and its monitoring change. Expiry never resumes trading or permits ownership theft, and seed/reset cannot remove active or completed-owner history.
- Each repository/workflow run has a stable UUID v5 owner across attempts; each execution report remains attempt-specific. The database retains every completed owner and permits only one active fence. A later cutover cannot erase an earlier owner's replay protection.
- Existing-release infrastructure updates preserve the PostgreSQL administrator password so versioned source ops credentials remain valid. Database-side credential rotation requires a separately coordinated operation; the Key Vault/release secret workflow alone does not perform it.
- Missing workloads never prove an empty database. Authoritative resource inventories distinguish a new foundation, an existing foundation requiring inspection, and a complete release; partial, inconsistent, or unavailable inventory blocks mutation. Fresh production paths repeat bounded, catalog-only PostgreSQL inspection before foundation, release, and migration changes. The versioned PostgreSQL 17 profile requires zero retained schema/database objects, large objects, database/global role settings, changed privileges, and annotations, plus absent runtime roles. Extension membership cannot hide application state; old or incomplete reports fail admission. Retained application objects, migration history, runtime roles, and stopped or incompatible state cannot be reset or reclassified as fresh.
- The temporary inspector reuses only the migrate-init slot, existing ops identity, and exact `direct-url` access. New foundations stage that already-planned binding earlier; existing foundations missing it fail without credential/grant repair. The first release preserves the inspected binding, checks runtime credential consistency, and rechecks emptiness inside migrate-init before any migration, role/password bootstrap, or seed.
- Inspector cleanup requires the downloaded canonical report, unchanged owned configuration, and exactly one known terminal execution. Uncertain creation/start, absent evidence, drift, or another execution retains the job and blocks release; deletion failure and evidence expiry during cleanup also block it. Recovery must inspect that retained resource rather than blindly delete, overwrite, or retry it. Azure inventory and PostgreSQL inspection are not a distributed transaction: workflow serialization, immediate rechecks, short evidence lifetimes, and explicit refusal remain required.
- Fence release requires the exact owner, reconciled/flat/lease-free state, verified disabled/Manual quiescence, and a new restore-verified baseline backup. Migration/backup, owned release, and target-smoke have separate retry checkpoints. Exact-owner release is idempotent; a failed smoke attempt retries without rerunning migration or reacquiring a consumed owner.
- Trusted production workflow code must match the deployed candidate SHA before any mutation. It attests actual Azure resource/image/quiescence readback with a purpose-bound GitHub OIDC audience; the ops job verifies the fixed issuer, repository IDs, main workflow, Environment, run/attempt, and invocation. Fence release checks the proof's 180-second freshness against database time after locking and journals only its verified provenance in the same transaction. Raw proofs stay private and are never published. This is workflow-attested readback, not an Azure signature or a distributed transaction.
- Transactional fence release independently checks the observed immutable image against the adapter's explicit expected release digest and journals that digest with the release. Candidate images cannot inherit the source digest's authorization. Exact-source compensation remains supported, including distinct source/candidate images built from the same commit.
- Pre-release failures retain the fence for owned recovery, not automatic expiry release. After release, disabled/Manual remains the execution guard even if smoke fails; smoke retries repeat live quiescence checks. Neither a released fence nor a successful disabled smoke authorizes production promotion or factory completion.
- Full production release runs publish a schema `2` immutable, workflow-attempt-bound receipt recording the admitted development run/attempt/workflow and distinguishing verified disabled/Manual, mutation-free deferral, and failure. Schema `1` releases remain historical records, not new admission authority. A foundation, green no-op, or partial release cannot substitute for that evidence.
- Read-only production verification binds fresh approval to the exact trusted smoke row. Its scheduled phase requires a fresh, purpose-bound `production-promotion` workflow proof, not caller-supplied timestamps: Azure readback establishes paper/Schedule enablement, then fully enumerates and verifies the unique successful hourly execution in the first full UTC-hour window. The exact execution endpoint must agree on identity, timing, immutable image, command, secret references, environment and container resources; runtime and schedule bindings must remain unchanged. The collector only reads Azure and never manually starts the hourly job.
- Schema `1.3.0` production reports bind that authenticated observation to the image/generation/hour AgentRun and require its completion within the observed Azure execution. Journaled outcomes, reconciled exact-decimal balances, released leases/fences, and inactive stops remain mandatory; a legitimate paper fill may leave an open position. Azure does not expose execution trigger origin, so evidence explicitly says `schedule-observed-not-origin-proven` rather than claiming manual starts are impossible. These proof helpers do not enable production or prove external telemetry/mailbox delivery.
- Trusted native workflows own automatic paper promotion under the approved design. Models do not perform deployment mutations. Automation may pause or disable on failure but must never clear operator/drawdown/emergency stops or expose secrets.
- POC promotion requires current-head reviews, exact-release provenance, healthy disabled smoke and zero-fill shadow, current restore proof, reconciled accounting, released leases/fences, and basic independent failure alerts. Actual scheduled paper execution must then be verified before delivery is complete.
- PostHog capture and explicit `dev`/`prod` tags remain; separate projects and private backend-query credentials are optional. Email provider acceptance must correlate with its journal audit but is not final mailbox delivery. Keep versioned private evidence and existing retention; an irreversible retention-policy lock and formal response sign-off are optional, not activation gates. Never shorten/delete an existing policy as a shortcut.
- Successful disabled smoke has no additional manual gates. Preflight still requires restore-verified backup and later activation evidence, enforced by the native release pipeline rather than a new per-release human approval. Failed checks retain explicit remediation; empty manual gates never authorize promotion or clear a stop.
- Validate with the narrowest applicable lint/build/test/migration/agentic checks and the isolated mock-first harness; real-provider smoke is opt-in and read-only.
- Standing paper-delivery authority is defined in `specs/governance.md`. Commissioning, exact external protection/credential changes, and initial activation remain separately scoped; routine verified releases do not require a new human approval. Source changes alone are not operational proof.
