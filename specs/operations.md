# Operations
- Dev and production are real Azure Container Apps/Jobs deployments of a permanently paper-only POC. Dev uses monitored `shadow`; production releases land `disabled`/Manual before evidence-gated promotion to scheduled `paper`. Until that promotion path is implemented, reviewed, and commissioned, production remains disabled/Manual.
- Releases use OIDC/Entra, least privilege, private PostgreSQL, immutable image digests, distinct runtime/owner/operator identities, replay-safe migrations, exact-SHA evidence, and independent alerts.
- Any failed identity, migration, smoke, reconciliation, backup/restore, evidence, schedule, or alert check stops the release; rollback first forces `Manual` plus `disabled`.
- Existing production releases require an ops-owned, signed-source-bound cutover fence before forced disable. A healthy open position or active lease defers the upgrade without changing mode, schedules, credentials, images, or balances; malformed, expired, stopped, or unreconciled state blocks it.
- Runtime admission and paper execution reject an unreleased fence; the runtime role has read-only fence access. Ownership and the six-hour deadline are revalidated at mutation boundaries, including forced disable and its monitoring change. Expiry never resumes trading or permits ownership theft, and seed/reset cannot remove active or completed-owner history.
- Each repository/workflow run has a stable UUID v5 owner across attempts; each execution report remains attempt-specific. The database retains every completed owner and permits only one active fence. A later cutover cannot erase an earlier owner's replay protection.
- Existing-release infrastructure updates preserve the PostgreSQL administrator password so versioned source ops credentials remain valid. Database-side credential rotation requires a separately coordinated operation; the Key Vault/release secret workflow alone does not perform it.
- Fence release requires the exact owner, reconciled/flat/lease-free state, verified disabled/Manual quiescence, and a new restore-verified baseline backup. Migration/backup, owned release, and target-smoke have separate retry checkpoints. Exact-owner release is idempotent; a failed smoke attempt retries without rerunning migration or reacquiring a consumed owner.
- Trusted production workflow code must match the deployed candidate SHA before any mutation. It attests actual Azure resource/image/quiescence readback with a purpose-bound GitHub OIDC audience; the ops job verifies the fixed issuer, repository IDs, main workflow, Environment, run/attempt, and invocation. Fence release checks the proof's 180-second freshness against database time after locking and journals only its verified provenance in the same transaction. Raw proofs stay private and are never published. This is workflow-attested readback, not an Azure signature or a distributed transaction.
- Pre-release failures retain the fence for owned recovery, not automatic expiry release. After release, disabled/Manual remains the execution guard even if smoke fails; smoke retries repeat live quiescence checks. Neither a released fence nor a successful disabled smoke authorizes production promotion or factory completion.
- Full production release runs publish an immutable, workflow-attempt-bound receipt distinguishing verified disabled/Manual, mutation-free deferral, and failure. A foundation, green no-op, or partial release cannot substitute for that evidence.
- Read-only production verification binds fresh approval to the exact trusted smoke row, and scheduled proof to the actual image/generation/hour AgentRun. It requires journaled outcomes, reconciled exact-decimal balances, released leases/fences, and inactive stops; a legitimate paper fill may leave an open position. These proof helpers do not enable production or prove external telemetry/mailbox delivery.
- Trusted native workflows own automatic paper promotion under the approved design. Models do not perform deployment mutations. Automation may pause or disable on failure but must never clear operator/drawdown/emergency stops or expose secrets.
- POC promotion requires current-head reviews, exact-release provenance, healthy disabled smoke and zero-fill shadow, current restore proof, reconciled accounting, released leases/fences, and basic independent failure alerts. Actual scheduled paper execution must then be verified before delivery is complete.
- PostHog capture and explicit `dev`/`prod` tags remain; separate projects and private backend-query credentials are optional. Email provider acceptance must correlate with its journal audit but is not final mailbox delivery. Keep versioned private evidence and existing retention; an irreversible retention-policy lock and formal response sign-off are optional, not activation gates. Never shorten/delete an existing policy as a shortcut.
- Successful disabled smoke has no additional manual gates. Preflight still requires restore-verified backup and later activation evidence, enforced by the native release pipeline rather than a new per-release human approval. Failed checks retain explicit remediation; empty manual gates never authorize promotion or clear a stop.
- Validate with the narrowest applicable lint/build/test/migration/agentic checks and the isolated mock-first harness; real-provider smoke is opt-in and read-only.
- Standing paper-delivery authority is defined in `specs/governance.md`. Commissioning, exact external protection/credential changes, and initial activation remain separately scoped; routine verified releases do not require a new human approval. Source changes alone are not operational proof.
